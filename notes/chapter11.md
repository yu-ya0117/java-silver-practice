## 用語集
- abstract：「抽象的」「曖昧」という意味の英単語、ここでは処理内容が未定という意味のキーワード。
- 抽象メソッド：処理内容が未定のメソッドのこと。abstractがつく。
- 抽象クラス：処理内容が完全に確定していない、サブクラスに実装を委任する設計図のようなクラス。abstractがつく。
- インタフェース：クラスが備えるべきメソッドの仕様だけを定義した、抽象度が高い抽象クラス。

## 1. 未来に備えるための継承

### 1.1 高度な継承を学ぶにあたって

chapter10では「継承」について学んだ。  
また、正しい継承は汎化・特化の関係の関係を表すことも学んだ。  
継承ツリーを親クラス、その親クラスと辿っていくほど、  
クラスは曖昧で抽象的なものになっていく。  

chapter11では、継承ツリーの上方に位置する「曖昧なクラスたち」の定義方法について学習する。  
これまでに学んできた方法でこれらのクラスを定義しても、プログラムは動作する。  

この「曖昧なクラスたち」専用のクラスの定義方法を理解し、高度な継承を実現すれば、  
より安全で便利にクラスを利用できるようになる。

この後抽象化やインタフェースというものを学んでいく。  
なんだか名前からして難しそうと思いがちだが、  
コツを1つ知っておくだけでグンと楽になる。

しかし、残念なことにchapter10の継承はすぐ理解できたのに、  
高度な継承が絡む段階でつまずくケースも珍しくない。  
この高度な継承をスムーズに理解するためには、  
これまで持っていたある意識を切り替える必要がある。

### 1.2 新しい「立場」で考える

高度な継承は文法的には難しいものではない。  
それでも多くの人がつまづく理由は、  
高度な継承を使うときの「立場」がこれまでの「立場」とは全く違うということを意識せずに学習を始めてしまうため。  

今まで自分たちはどんな「立場」でJavaを使うことをイメージしてきただろう。  
多くの場合が、作るもの、あるいは作りたいプログラムが明確に決まっていて、  
そのプログラムのためだけに必要なクラスを作って目的のプログラムをかんせいさせる「立場」にあったと思われる。

もし開発すべきクラスと類似した「既存のクラス」があれば、  
継承を利用して子クラスにするより、  
イチから開発せずともいくつかのメンバを追加するだけで、  
効率よくクラスを開発することができた。

一つのプログラムはクラスA、クラスB、クラスCから成り立つとする。  
普通の開発者の場合は、このうちクラスAとBは自分で作成し、  
クラスCは既存クラスから継承して作成する。  
これらを組み合わせて一つのプログラムが完成する。  

ここで「既存のクラス」に焦点を当ててみる。  
きっとこのクラスを事前に開発しておいてくれた開発者がいるはず。  
その作者は、自分の作ったクラスがどんなプログラムに利用されるかは想像もつかない段階であり、  
「いつ誰かが、このクラスを継承して開発したら便利だろう」と未来に思いを馳せ、  
継承の材料として既存のクラスを作ってくれた。  
実にとてもありがたい話である。  

こう考えると、「普通の開発者（これを立場1とする）」の他に、  
「未来に備える開発者（これを立場2とする）」が存在することがわかる。  

立場1：現在、目の前のプログラム開発に必要なクラスを作る開発者  
（既存クラスを継承して子クラスを継承する側）

立場2：未来に備え、別の開発者が将来利用するであろうクラスを準備する開発者  
（親クラスとなるクラスを作っておく側）

これから高度な継承をスムーズに理解するためにも、  
この2つの立場の存在を明確に意識して区別するのが今回の学習のポイントである。

これまでは立場1のとして開発するために必要なものを学習してきた。  
これからは立場2としてプログラムを作る時に必要となるものである。  
これから学ぶ「抽象クラス」および「インタフェース」とは、  
立場2の人たちが立場1の人たちに安全に便利に使ってもらえる親クラスを作るための道具である。  
そのため、「未来に備える開発者の立場」でここからは学習してみよう。

ここでひとつ思ったことがある。  
Java APIの中にも「未来に備える開発者」が作ったものがあるのではないかと。  
もちろんfinalがつけられて継承できなくしているものも存在するだろう。

### 1-3. 「未来に備える開発者」の立場

たとえばゲーム開発の例で考えてみる。  
プロジェクトではAさん、Bさん、Cさん、Dさんの4人で開発を進めているが、  
ある日、開発効率が悪いことが問題になった。

Dさんがプロジェクト全体の開発効率を改善する責任者に任命されたとする。  
Dさんが調査したところ、開発者がそれぞれHeroやWizardなど、  
似たクラスをイチから作っていることに気づく。

[![Image from Gyazo](https://i.gyazo.com/18fff0bdd0e3af87eb1cbd08e64c9cf2.png)](https://gyazo.com/18fff0bdd0e3af87eb1cbd08e64c9cf2)

上図では、nameとhpのフィールド、attack()とrun()のメソッドが共通している。  
これらをそれぞれ別に開発するのは非効率である。  
また、今後のバージョンアップにより、「商人」や「占い師」など、  
さまざまな職業のキャラクターが増える予定だが、  
それらもイチから開発しては効率が悪い。

そこでDさんは各クラスに共通するフィールドやメソッドをGameCharacterクラスを準備し、  
各開発者に対しては、「このGameCharacterクラスを継承して、独自のフィールドやメソッドを追加するだけで大丈夫！」とアナウンスすればいい。  
(ここでGameCharacterにしている理由は、Java標準APIのCharacterクラスと区別するため)  

[![Image from Gyazo](https://i.gyazo.com/01f187dfc330f4fad340314f578aa961.png)](https://gyazo.com/01f187dfc330f4fad340314f578aa961)

上図の場合であれば、各開発者はHeroやWizard、Thiefなど、  
それぞれの職業に特有なフィールドやメソッドだけを開発すれば済むので効率的になる。  

このとき、Aさん、Bさん、Cさんは「今すぐ必要な実際に利用されるクラス」を作る、立場1の開発者である。  
一方でDさんは「未来に備えて継承元となるクラス（継承の材料）」を作るという、立場2の開発者にあたる。

開発プロジェクトの最前線で今すぐ必要なHero、Wizard、Thiefなどのクラスの開発をがんばるAさん、Bさん、Cさんに対して、  
Dさんは後方から開発の支援の道具(共通部分まで事前に作っておいたGameCharacterクラス)を供給して援護をしている。

これからは自分たちはDさんの立場になって学習を進める。  
たった1つのクラスの優劣が、それを利用する複数の開発者たちの開発効率に影響を与えることになる。  
立場2、つまり「未来に備える開発者」の役割とは、  
ほかの開発者が効率よく安心して利用できる継承の材料をつくることにある。

## 2. 高度な継承に関する2つの不都合

### 2-1. 2つの不都合、3つの心配

じゃGameCharacterクラスを作れば一件落着...とはならない。  
他の開発者への心配りをを強く意識してGameCharacterのようなクラスを開発していると、
2つの「不都合」に直面する。  
さらに、「不都合」を原因とする、さまざまな「心配事」も出てくる。  
「抽象クラス」や「インタフェース」はこれらの心配事を解決してくれる道具である。

継承の材料となるクラスに関する2つの「不都合」と3つの「心配事」は以下の関係にある。

[![Image from Gyazo](https://i.gyazo.com/fadbb0d6353426a52b2b8868df81b35c.png)](https://gyazo.com/fadbb0d6353426a52b2b8868df81b35c)

次から1つずつ「不都合」と「心配事」について見ていく。

### 2-2. 最初の不都合

最初の不都合Aを体験するために、  
実際にGameCharacterクラスを途中まで作成してみる。

```
public class GameCharacter {
    String name;
    int hp;

    //逃げる
    public void run() {
        System.out.println(this.name + "は逃げ出した");
    }

    //戦う
    public void attack(Matango m){
        System.out.println(this.name + "の攻撃！");
        m.hp -= ??;     //  ここを記述しようとして手が止まる
        System.out.println("敵に？？ポイントのダメージをあたえた！");  //  ここの値も記述できない
    }
}
```

なぜ手が止まってしまったのかを深掘りしてみる。  
このGameCharacterクラスは将来、様々な開発者によって継承され、  
HeroやWizard、Dancerなどを開発する際の材料として利用される。

未来に完成するであろうHeroやWizard、Dancerは、  
それぞれお化けキノコを攻撃したときに与えるダメージが違うはず。  

攻撃力の高いHeroは与えるダメージは10ポイント、  
直接攻撃が苦手なWizardは5ポイント、  
今は存在しないが、未来に追加するかもしれない強力なキャラクターでは100ポイントなどもありえる。

つまり、今現在でGameCharacterを作成している時点では、
**attackメソッドの処理内容を確定できないため、書きようがない**ということになる。

「不都合A」とは、  
継承の材料となるクラスを作成する時点では、  
その処理をまだ確定できない詳細未定のメソッドが存在する。

### 2-3. 不都合Aに対する間違った解決方法

attackメソッドのような内容を確定できないメソッドをどのように記述すればいいのだろうか？

まず思いつきやすいのは、GameCharacterクラスにはattackメソッドを記述しない方法。  
HeroやWizardなどの新しいキャラクタークラスを作成するときに、  
それぞれの継承先のクラスでattackメソッドを追加してもらう。

しかしこの方法で不都合を解決しようとすると、  
他の開発者が将来、新しいキャラクタークラスを作成するときに、  
もし継承先にattackメソッドを継承し忘れると「攻撃できないキャラクター」ができてしまう。

そもそも「ゲームの世界の全てのキャラクターはHP属性を持ち、攻撃ができる」という前提でGameCharacterクラスを作り始めたのに、  
「attack()を持たないキャラクター」ができてしまっては困る。  
それでは各自でattackメソッドをつけ忘れないように気をつければいいのではないかという疑問も出てくるが、  
いくら気をつけてもミスは完全にはなくならない。  
そのため、「ミスを防止する仕組み」を考える必要がある。

そもそもオブジェクト指向とは、  
「現実世界（今回の場合はゲームのキャラクターたちが住む世界）を仮想世界に正確に写し取る」ことである。
「キャラクターであれば少なくとも攻撃ができるはず」というゲームの世界の前提を考えると、  
攻撃できないキャラクターが作れてしまう可能性は万が一にもあってはならない。  
GameCharacterクラスは必ずattackメソッドを持っているべきである。

現実世界に対応したメソッドの必要性を簡単にまとめると、  
「現実世界の登場人物が持つ操作」であれば、  
クラスのメソッドも存在すべきである。  
メソッドの処理内容は確定困難であったとしても例外ではない。

### 2-4. 不都合Aに対する対応策と2つの心配事

不都合A(「詳細未定のメソッド」の存在)の対応策として、  
「GameCharacterクラスのattackメソッドは内容が確定していないので、とりあえず空にしておこう」と思いつくかもしれない。  
他の開発者がattackメソッドを継承してそれぞれのキャラクタークラスを作成する際に、  
その職業に最適なattackメソッドでオーバーライドしてもらうということである。

GameCharacterクラスのイメージは以下の通り。

```
public class GameCharacter {
    String name;
    int hp;

    //逃げる
    public void run() {
        System.out.println(this.name + "は逃げ出した");
    }

    //戦う
    public void attack(Matango m){
    }
}
```

未来の開発者が作成するHeroクラスのイメージは以下の通り。

```
public class Hero extends GameCharacter {
    public void attack(Matango m) {
        System.out.println(this.name + "の攻撃！");
        System.out.println("敵に10ポイントのダメージを与えた！");
        m.hp -= 10;
    }
}
```

なかなか悪くない方法ではある。  
しかし、GameCharacterクラスを利用してくれる未来の開発者たちを思いやる気持ちが強いほど、  
次の2つの心配事がよぎることだろう。

### 2-5. 第1の心配事：オーバーライドを忘れる

未来の開発者がHeroやWizardなど具体的な職業クラスを作る際に、  
attack()をオーバーライドし忘れると重大な不具合に繋がってしまう。

例えば、以下のようにHeroクラスでattack()をオーバーライドし忘れたとする。

```
public class Hero extends GameCharacter {
  // attack()をオーバーライドし忘れる
}
```
```
public class Main{
    public static void main(String[] args) {
        Hero h = new Hero();
        Matango m = new Matango();
        h.attack(m);  //  メソッドは呼び出せるが何も起きない...。
    }
}
```

HeroクラスはGameCharacterクラスから内容が空のメソッドを受け継いでいる。  
そのため、他のメソッドからattackメソッドを呼び出せるが何も起きないという不具合を抱えたクラスになってしまう。

解決案の1つとして、GameCharacterクラスのattackメソッドを作成するときに、  
コメントを残しておくという方法がある。

しかし、GameCharacterを継承する未来の開発者が、  
コメントを見逃したり、無視したりする可能性はある。  
仮に無視しなかったとしても、以下のようなミスをする場合もある。

```
public class Hero extends GameCharacter {
    public void atack(Matango m) {    //  attackのスペルミス
        System.out.println(this.name + "の攻撃！");
        System.out.println("敵に10ポイントのダメージを与えた！");
        m.hp -= 10;
    }
}
```
これはオーバーライドできているようでオーバーライドできていないパターン。  
処理の中身が空のattack()と自分で定義したatack()の2つのメソッドを持ってしまう。
このHeroクラスの作者にとっても「自分はちゃんとattack()をオーバーライドして空の処理を上書きした」と思い込んでしまっているだろう。  
これではこのHeroクラスの作者にとっても、それを呼び出す開発者にとっても、  
なぜ正しい攻撃ができないのか頭を抱えることになるだろう。

### 2-6. 第2の心配事：「本当になにもしない」と区別がつかない

もう一度GameCharacterのattackメソッドをよく見てみよう。

```
public class GameCharacter {
    String name;
    int hp;

    //逃げる
    public void run() {
        System.out.println(this.name + "は逃げ出した");
    }

    //戦う
    public void attack(Matango m){
    }
}
```

そもそもこの書き方は、「メソッドが呼ばれても何もしない」メソッドを作りたい場合に行うものである。  
しかし、今回のattack()は「何もしない」のではなく、「何をするのかが未定で記述できない」。  
未来の開発者がこのメソッドを見たとき、  
「何もしないのが正しい」か、「何をするのか未定」なのか、  
区別がつかない恐れがある。

### 2-7. 第3の心配事：意図せずnewして利用されてしまう

これまでは不都合A、すなわち「詳細未定のメソッドが存在する」ことに対する2つの心配事について考えてきた。  
3つ目の心配事は、これらとはまったく別の観点からの心配事である。  
それは、「未来の開発者が間違ってGameCharacterクラスをnewして利用してしまうかもしれない」という心配である。

例えばプロジェクトに新しく入ったJava初心者のEさんに、  
「便利なクラスだからどうぞ使ってください」とGameCharacterクラスを渡したら、  
Eさんは次のようなコードを書いてしまうかもしれない。

```
public class Main{
    public static void main(String[] args) {
        GameCharacter gc = new GameCharacter();   //  HeroやWizardではなくGameCharacterをnewしてしまった。
        Matango m = new Matango('A');
        gc.attack(m);   //  中身がないので何もできない！
    }
}
```

これは完全に間違った使い方である。  
このGameCharacterクラスは継承材料として使うべきであり、  
HeroやWizardクラスみたいにnewして使うものではない。  
GameCharacterクラスが作られた経緯を知らない人やJava初心者の人は、  
間違ってnewするかもしれない。

実はGameCharacterクラスから実体であるインスタンスが生み出されたり、  
そのインスタンスが仮想世界の中で活動してしまったりするのはかなりの異常事態である。  
なぜなら、詳細未定なattackメソッドを含むGameCharacterクラスは、  
詳細未定につき、作り込んでいない部分が残っている未完成な設計図のようなものだからである。

GameCharacterクラスに限らず、未来の開発者のために準備しておくクラスは、  
多かれ少なかれ未完成な部分が残っているもの。  
そのような設計図に基づいて、実体である製品（たとえば車）を生産して利用したら大変な事故につながる。

まとめると、このGameCharacterのように、一部でも「詳細未定」な部分が残っているクラスはインスタンス化してはいけない。

### 2-8. 第3の心配事の原因

なぜ3つ目の心配事(間違ってnewされてしまう心配)が出てきてしまったのだろうか？  
そもそもクラスには2つの利用方法がある。

1. newによる利用：インスタンスを生み出すためにそのクラスを利用する。
2. extendsによる利用：イチからクラスを開発すると効率が悪いので、あるクラスを継承元として利用する。

1はHeroやWizardクラスなど詳細未定のメソッドがない完成されたクラスで利用される。  
これらはnewしてインスタンスを生成するのが正しい使い方である。

2はGameCharacterなど継承の材料となるクラスで利用される。  
正しい使い方としては、extendsして他のクラスを作る際に継承元（材料）にする。

しかし残念なことに、いくらGameCharacterクラスの作者が「extendsして利用してほしい」と願っても、  
未来の開発者はnewによる利用とextendsによる利用のどちらも選べてしまう。  
そのため、GameCharacterのような未完成なクラスが誤ってnewされてしまうという事態が発生する。

ここで不都合Bについてまとめると、  
クラスには2つの利用方法(newによる利用、継承による利用)があり、  
開発者それを自由に選ぶことができる。  
この不都合Bが、第3の心配事「意図しないnewの利用」の原因となっている。

これを解決するために、第1の心配事と同様に、  
ソースファイルの先頭にコメントを書くというアイデアも考えられるが、  
読み落としたり、無視されたりする可能性がある。

それではこの不都合や心配事をどうやって解決すればいいのだろうか？  

もし自分が作ったGameCharacterクラスが、  
未来の開発者によって正しくない使われ方をされて不具合の原因にならないか不安だ。
